## 2. حدود النطاق والاعتماديات

**نطاق التنفيذ المقترح هو Frontend فقط.** يشمل بناء App Shell وهيكل وتجربة الصفحات وحالاتها البصرية بالعربية والإنجليزية، دون إضافة Backend أو endpoints أو تعديل عقود API.

تغييرات المصادقة والجلسات والأدوار والصلاحيات وحماية المسارات القائمة خارج النطاق، ما لم يصدر اعتماد منفصل صريح. يجب أن يحافظ تنفيذ App Shell على سلوك المصادقة والجلسات وحماية المسارات الحالي دون تعديل، بما في ذلك السلوك القائم الذي لم يُتحقق من سلامته خادميًا. لا تُستنتج صلاحيات جديدة من عناصر التنقل أو الأدوار التجريبية. تُوثّق المشكلات القائمة دون إصلاحها ضمن هذه المهمة، ويُطلب اعتماد منفصل قبل أي تغيير يمس هذا السلوك.

لا تُغيّر واجهة API أو أنواعها الحالية، ولا تُخترع حقولًا أكاديمية أو قواعد بيانات أو سياسات منتج. يمكن للواجهة استهلاك بيانات موجودة عبر العقود الحالية فقط؛ وما لا يتوفر يعرض حالة صريحة، لا بيانات بديلة.

المشروع يستخدم Next.js App Router مع locale segment وNext Intl، وReact/TypeScript، وTailwind CSS 4، وZustand، وTanStack Query، وLucide، وMotion/GSAP، وBase UI/shadcn. لا يظهر احتياج مثبت لإضافة مكتبة جديدة.

توجد فجوات بين README والتنفيذ الفعلي: README يصف ملفات تنظيم وتهيئة غير موجودة، ويذكر next-themes بينما المظهر يُدار عبر مزوّد محلي ولا تظهر الحزمة ضمن الاعتماديات. src/lib/api.ts يستخدم fetch بينما src/lib/axios.ts فارغ. كذلك يذكر README أن npm run check يشغّل الاختبارات، لكن script الفعلي يشغّل type-check وlint وformat-check وbuild فقط. نعتمد package.json والكود الفعلي عند اختيار الأوامر.

## 3. خريطة المسارات وقرار المواد

المسارات المكتشفة حاليًا: الصفحة الرئيسية، login، about، contact، departments، get-started، resources، subjects، dashboard، admin، وPOST /api/contact. المسارات العامة الحالية تبقى دون تغيير في هذا النطاق.

فُحصت بنية Next.js الفعلية قبل توثيق القرار:

- صفحة المواد العامة موجودة في app/[locale]/(public)/subjects/page.tsx، ولذلك مسارها هو /[locale]/subjects.
- Dashboard الطالب موجودة في app/[locale]/(student)/dashboard/page.tsx، ومسارها الحالي هو /[locale]/dashboard؛ اسم route group بين القوسين لا يظهر في URL.
- لا يوجد حاليًا مسار /[locale]/student/* أو layout داخل مجموعة (student). layout الخاص باللغة في app/[locale]/layout.tsx يغلّف الصفحات المحلية كلها، وapp/[locale]/(public)/layout.tsx يخص المجموعة العامة فقط.
- middleware.ts يطابق المسار الجذري والمسارات المحلية /en/* و/ar/* ويهيئ next-intl؛ لا يوجد مسار آخر يبدأ بـ /student حاليًا.
- وضع صفحة مستقبلية تحت app/[locale]/(student)/student/subjects/page.tsx ينتج المسار المحلي /[locale]/student/subjects ولا يتعارض مع الصفحة العامة /[locale]/subjects. هذا توثيق لخريطة المسارات فقط، ولم تُنشأ الصفحة.

**قرار المواد المعتمد من المستخدم:** الإبقاء على /[locale]/subjects للصفحة العامة الحالية، وإضافة تجربة مواد الطالب تحت /[locale]/student/subjects. لا يُغيّر سلوك المسار العام.

**خريطة المسارات المحلية المعتمدة للتخطيط:** المسارات أدناه لا تتضمن بادئة اللغة؛ تضيف بنية المشروع بادئة اللغة الفعلية تلقائيًا، مثل /ar أو /en. Dashboard تبقى مؤقتًا على مسارها الحالي /[locale]/dashboard، ولا تُنقل ولا يُنشأ لها alias إضافي دون حاجة واعتماد منفصل.

## 4. عقود البيانات والمصادقة

- المصادقة هي الخدمة الوحيدة غير الفارغة: src/services/auth.service.ts يعرّف login وme وrefresh وlogout. src/lib/api.ts يرسل الطلبات إلى NEXT_PUBLIC_API_URL أو افتراضيًا http://localhost:4000/api/v1. توجد أنواع استجابة أمامية في src/types/auth.ts، لكن لا يوجد Backend في هذا المستودع للتحقق من مطابقتها.
- .env.example وREADME يشيران إلى API على المنفذ 3000، بينما fallback في API client على 4000. لا يوجد ملف .env محلي لتحديد القيمة المقصودة. هذا العنوان غير محسوم، ولا تجري محاولة لإصلاحه أو تغيير إعداداته في هذه الخطوة.
- AuthUser.roleName نص عام، وStudentProfile يضم studentCode وfullName وacademicYear فقط. لا توجد حقول college/department/semester أو نطاق معتمد/معلق أو بيانات content year.
- src/hooks/use-auth-guard.ts يصف الحماية بأنها UX فقط ويستدعي /auth/me. middleware.ts يثبت next-intl فقط؛ لا يوجد كود Backend أو تحقق صلاحيات خادمي داخل المستودع. عند فشل الشبكة غير 401 يبقى guard الحالي دون حالة خطأ واضحة. هذه ملاحظات تدقيق فقط؛ لا تُغيّر المصادقة أو الجلسات أو الأدوار أو حماية المسارات عند بناء App Shell.
- يجب ألا يستنتج App Shell صلاحيات من ظهور عنصر تنقل أو من دور حساب تجريبي. يحافظ التنفيذ على السلوك الحالي كما هو، وتُوثق أي مشكلة قائمة دون إصلاحها. أي تغيير غير مباشر أو مباشر في المصادقة أو الجلسة أو الحماية يتطلب اعتمادًا منفصلًا.
- ملفات صفر بايت ذات صلة: ملفات roles/permissions وroute/config وauth/axios/interceptors، أنواع user/subject/summary/quiz/notification/API والطلبات والاستجابات والتصفح، schemas للخدمات، وخدمات subject/summary/quiz وmiddleware الصلاحيات. ملف التواصل app/api/contact/route.ts لا يوفر عقدًا لبيانات الطالب. لم تُستكمل هذه الملفات أو تُصلح في Phase 1.
- التعديل المحلي السابق في auth.service.ts يوفّر حسابات تطوير تجريبية بطلب سابق من المستخدم؛ هي ليست بيانات طالب حقيقية أو تكامل Backend. حساب sadmin التجريبي يُعاد حاليًا بدور admin، فلا يثبت وجود تمييز Super Admin في العقد. لا تُغيّر هذه السلوكيات ضمن النطاق الحالي.

**معايير قبول حالات الواجهة:**

- تُبنى البنية البصرية الكاملة للصفحات والحالات المعتمدة حتى عندما لا تتوفر بيانات؛ عرض الصفحة وحده لا يعني اكتمال وظيفة أو تكامل.
- لا تُعرض فلاتر أو محددات سنة/فصل/سنة محتوى على أنها تفاعلية ما لم توجد بيانات وعقود تدعمها. إذا لم تكن الميزة مدعومة، تُخفى عناصر التحكم أو تعرض حالة عدم توفر واضحة بحسب تصميم الصفحة.
- غياب الخدمة أو عدم دعمها يُعرض كحالة غير متاحة. أما الخدمة المدعومة التي تعيد صفر سجلات فتعرض حالة فارغة. تظل أخطاء الشبكة و401 و403 حالات مميزة ولا تُحوّل إلى قائمة فارغة.
- لا يتغير عنوان API أو العقود لمحاولة جعل الواجهة تبدو عاملة. ولا يعلن اكتمال تكامل لمجرد عرض الصفحة دون أخطاء.
- لا تستخدم بيانات أو fixtures تجريبية في تشغيل الموقع؛ fixtures واعتراضات الشبكة مسموحة داخل اختبارات معزولة موسومة بوضوح فقط، ولا تثبت تكامل Backend أو صلاحياته.

**قاعدة التنفيذ بعد اعتماد التقرير:** اكتمال هيكل الصفحة لا يعني اكتمال الوظيفة. كل قراءة/كتابة/إجراء لا يُفعّل إلا عبر عقد حقيقي؛ غير ذلك تظهر حالته بصراحة ولا تُملأ الصفحة بمقاييس أو أسماء أو نتائج مختلقة. لا تُضاف أدوار أو مستويات أو XP أو اختبارات قادمة أو جدول دراسي، ولا تتغير السنة الأكاديمية بتغيير سنة المحتوى.

## 6. قرارات المنتج المفتوحة

لا تحسمها ملفات المستودع، ولا تتحول إلى سلوك افتراضي في الواجهة: القوائم الأكاديمية الرسمية؛ حقول التسجيل والتحقق؛ تعريف اكتمال المحتوى؛ قيم النقاط وشروط الإنجازات؛ كسر تعادل Leaderboard؛ سياسة الإعادة واحتساب نقاطها؛ مدة الاختبار ومواعيده وحد النجاح وأنواع الأسئلة ومراجعة الإجابة؛ قنوات الإشعارات وخصوصية حقول Profile؛ وسياسات AI للاحتفاظ والملفات والوصول إلى محتوى المنصة.

عنوان API وعقود بيانات الطالب فجوات تكامل/Backend وليست قرارات واجهة. المصادقة والجلسات والأدوار والصلاحيات وحماية المسارات مستثناة من النطاق الحالي، وأي تغيير فيها يحتاج اعتمادًا منفصلًا.

## 7. الفحوص المتاحة ونتائجها في Phase 1

- scripts الموجودة: type-check وlint وformat-check وtest (Vitest) وe2e (Playwright) وbuild وcheck وcheck:full.
- Vitest يضم اختبار توافق مفاتيح الترجمة. Playwright يضم فحوصًا للصفحات العامة، الاتجاه/الثيم والتجاوب، تنقل الهاتف واللغة، وحالات resources/subjects وredirect للمسارات المحمية.
- **لم تُشغّل الفحوص في Phase 1 أو عند تحديث هذا التقرير.** لذلك لا توجد نتيجة نجاح أو فشل مسجلة. نجاح اختبارات UI مستقبلًا لن يثبت صلاحيات Backend أو تكامله الحقيقي.

## 8. القرارات المحسومة والبوابة المطلوبة

**قرارات النطاق والمسارات المحددة:** نطاق Frontend فقط؛ لا Backend أو تغييرات عقود API؛ لا تغييرات auth/session/roles/permissions أو حماية المسارات دون اعتماد منفصل؛ الحفاظ على كل المسارات العامة؛ الإبقاء على /[locale]/subjects عامًا؛ إنشاء تجربة مواد الطالب على /[locale]/student/subjects؛ اتباع صفحات الطالب الجديدة نمط /[locale]/student/<page>؛ والإبقاء على Dashboard مؤقتًا على /[locale]/dashboard دون نقل أو alias إضافي. يجب إعادة التحقق من route tree وlayouts وmiddleware قبل التنفيذ.

**ما زال مفتوحًا:** عنوان وبيئة API وعقود البيانات؛ البيانات الأكاديمية الرسمية؛ وقرارات المنتج المذكورة في القسم 6. نقص API يمنع تشغيل العمليات أو عرض بيانات متخيلة، لكنه لا يمنع بناء هيكل الصفحة وحالاتها البصرية الصادقة.

**سجل الاعتماد:** اعتمد المستخدم الإصدار الثالث صراحةً، وفتح بوابة التنفيذ ضمن النطاق المحدد أعلاه. لا يجيز هذا الاعتماد إضافة Backend أو تغيير عقود API أو المصادقة والجلسات والأدوار والصلاحيات وحماية المسارات، أو اختراع بيانات وسياسات وقرارات منتج غير معتمدة.
